# Model Evaluation

**Denmark Road Assistant — Explainable Machine-Learning Route Advisory System**

Every number in this document was produced by a command in this repository. The
commands are given so each figure can be reproduced.

Reproduce everything with:

```bash

rm -f models/road_condition_model.joblib models/road_condition_model_metadata.json data/synthetic_denmark_routes.csv
./.venv/Scripts/python.exe -c "import sys; sys.path.insert(0,'.'); from app.main import manager; manager.startup()"
./.venv/Scripts/python.exe scripts/live_distribution_sweep.py
```

---

## 1. The task

Given an origin, a destination and a departure time in Denmark, grade the driving
conditions on the route as one of five ordered classes — **Excellent, Good,
Moderate, Poor, Very Poor** — and say how many minutes early the driver should
leave.

This is a **five-class ordinal classification** problem. It is treated as plain
multi-class classification; the ordering is not encoded in the loss, which is a
limitation discussed in §9.

---

## 2. The dataset

| | |
|---|---|
| Source | Synthetic, generated by `ml-service/app/dataset.py` |
| Rows | 12 000 |
| Features | 19 (15 numeric, 4 categorical) |
| Target | `road_condition_label`, 5 classes |
| Split | 80 / 20 stratified train/test → 9 600 train, 2 400 test |
| Seed | 42 — regenerating produces a byte-identical file |
| File | `ml-service/data/synthetic_denmark_routes.csv` (1.6 MB) |

### How a row is made

The generator does **not** know how to compute a single feature. It invents a
plausible *observation* — a distance, a realised journey time, a departure
timestamp, how built-up the endpoints are, and some weather — and hands it to
`features.derive_features()`. That is the same function the live prediction
endpoint calls. §4 explains why this matters more than anything else in this
report.

Observations are sampled from three route archetypes (city / suburban /
regional) and five weather severity bands (calm / mild / wet / severe /
extreme), across all 24 hours and all 365 days of a year.

### Class balance — before and after

The original model's training set was built by code that is not in this
repository (see §8). Its balance, measured on the shipped CSV, and the balance of
the current generated set:

| Class | Before (old CSV) | | After (current) | |
|---|---:|---:|---:|---:|
| Excellent | 1 584 | 13.20 % | 2 672 | 22.27 % |
| Good | 3 936 | 32.80 % | 3 042 | 25.35 % |
| Moderate | 4 629 | 38.57 % | 3 540 | 29.50 % |
| Poor | 1 729 | 14.41 % | 1 782 | 14.85 % |
| **Very Poor** | **122** | **1.02 %** | **964** | **8.03 %** |

The change did **not** come from editing labels. It came from sampling weather
across severity bands instead of from a three-valued lookup on the season, so
severe conditions actually occur in the data. See §9 for what that means for
interpreting these priors.

## 3. The model

`sklearn.pipeline.Pipeline`:

1. `ColumnTransformer` — numeric features passed through, 4 categorical features
   one-hot encoded (`handle_unknown="ignore"`).
2. `RandomForestClassifier`.

| Hyper-parameter | Value | Why |
|---|---|---|
| `n_estimators` | 200 | Down from 280; no measurable accuracy cost |
| `max_depth` | 18 | Was unlimited. The main reason the old artefact was 82 MB |
| `min_samples_leaf` | 4 | Was 2. Fewer, larger leaves; less overfitting and much smaller |
| `class_weight` | `balanced_subsample` | Keeps the rarer grades learnable |
| `random_state` | 42 | Reproducibility |

**Artefact size: 82 MB → 8.9 MB**, a 89 % reduction, with accuracy *rising*. The
old file was too large to keep in Git at all; the new one is still git-ignored
because it is a build output, but it regenerates in about **5 seconds**.

## 4. The defect that mattered most: train/serve skew

Before this work, features were derived **twice, in two languages**:

* the Java backend computed all 19 features at prediction time;
* this Python service computed them differently when generating training data.

The formulas had drifted. Three of four checked features used different
constants, and the Java code had an entire `lowTrafficTime` branch with no
counterpart in training, which roughly halved `traffic_level` for any departure
between 22:00 and 07:00 — the single most important feature at the time.

**Measured consequence: live feature vectors occupied roughly 8 % of the training
distribution.** The model was extrapolating on nearly every real request.

There is now exactly **one** derivation, `ml-service/app/features.py`, called by
both the dataset generator and the prediction endpoint. Skew is not corrected —
it is structurally impossible, because there is no second copy to drift.


advertised was in reality a four-grade one.

### Confusion matrix

Rows are the true class, columns the predicted class, both in the order
Excellent → Very Poor.

| | Exc | Good | Mod | Poor | V.Poor |
|---|---:|---:|---:|---:|---:|
| **Excellent** | **478** | 56 | 0 | 0 | 0 |
| **Good** | 35 | **516** | 57 | 0 | 0 |
| **Moderate** | 0 | 62 | **593** | 53 | 0 |
| **Poor** | 0 | 0 | 39 | **291** | 27 |
| **Very Poor** | 0 | 0 | 0 | 20 | **173** |

This is the most informative result in the report. **Every single error is to an
immediately adjacent grade.** The model never once confuses Excellent with
Moderate, or Poor with Good. For an ordinal problem that is exactly the failure
mode you want: when it is wrong, it is wrong by one step, so the advice it gives
is still directionally correct.

The old matrix, by contrast, had an entirely empty final column
(`[5, 3, 3, 13, 0]` for the true Very Poor row) — 24 genuinely severe routes, all
misgraded as something milder.

## 7. Live prediction sweep (V13)

The question the old model failed: *in normal use, does the app ever actually
show all five grades?*

Grid: 8 real Danish route pairs × 4 seasons × weekday/weekend × 4 weather bands ×
6 departure hours = **1 536 predictions**, all through the live derivation path.

| Grade | Count | Share |
|---|---:|---:|
| Excellent | 313 | 20.4 % |
| Good | 546 | 35.6 % |
| Moderate | 332 | 21.6 % |
| Poor | 290 | 18.9 % |
| Very Poor | 55 | 3.6 % |

**All five grades occur.** (The old model produced zero "Very Poor" over an
equivalent sweep.)

More useful than the totals is the breakdown by weather, which shows the model
responding to the input rather than to a prior:

| Weather band | Predictions |
|---|---|
| calm | Excellent 183, Good 182, Moderate 19 |
| typical | Excellent 124, Good 211, Moderate 48, Poor 1 |
| wet | Excellent 6, Good 150, Moderate 190, Poor 38 |
| **storm** | Good 3, Moderate 75, **Poor 251, Very Poor 55** |

The gradient is monotonic and sharp: calm weather never produces Poor, and storms
never produce Excellent.

## 8. Reproducibility — a defect found during this work

The originally shipped `synthetic_denmark_routes.csv` **could not have been
produced by the generator committed alongside it.** Measured directly:

| Rows violating the committed generator's own arithmetic | Count |
|---|---:|
| `wind_speed_kmh < 5.0`, though the code forces `max(5.0, …)` | 149 |
| `avg_speed_kmh < 24.0`, though the lowest sampled band starts at 24 | 2 112 |
| `weather_risk` outside `[0.339, 0.670]`, the only interval a 3-valued season map can emit | **5 837** |
| `rainfall_mm > 6.18`, above the arithmetic maximum of `weather_risk × 8` | 1 451 |

`weather_risk` held 89 distinct values spanning 0.00–0.90, where the committed
code can emit three values ±3 %.

**The model that was answering requests had been trained by code that was never
committed.** Its reported accuracy of 0.7788 therefore belonged to a dataset
nobody could regenerate. That is a reproducibility failure on top of the
circularity in §9.

The current dataset and model regenerate deterministically from seed 42. A test
(`tests/`) asserts that `generate_dataset(200, seed=7)` returns identical frames
on two calls.

## 9. Limitations — read this before quoting any number above

**1. The labels come from a rule, so the accuracy is partly circular.**
`features.condition_score()` computes a difficulty score from a weighted sum, and
thresholds turn it into a grade. The model is then trained to reproduce that
rule. An accuracy of 0.8546 means *the Random Forest recovers the hand-written
rule 85 % of the time* — it does **not** mean the app is right about Danish roads
85 % of the time. No claim of real-world accuracy is made anywhere in this
project, and none should be.

The residual 15 % is not noise-free either: it comes from the deliberate label
noise (σ = 0.025 on the score) and from genuine ambiguity near the thresholds.

**2. Only the weather inputs are real.** `temperature_c`, `rainfall_mm`,
`humidity` and `wind_speed_kmh` are a live Open-Meteo forecast for the route
midpoint at the departure hour, verified to match Open-Meteo exactly. Everything
else — traffic, roadworks, accident exposure, road grade — is **derived from
assumptions**, not measured. There is no live traffic feed and no roadworks feed
in this system.

**3. The class priors are not Denmark's priors.** Weather is sampled from
stratified severity bands, deliberately over-representing storms, because a model
that has seen four severe hours cannot learn what a severe hour looks like. So
"Very Poor is 8 % of the training set" says nothing about how often Danish roads
are actually very poor. The live sweep's 3.6 % is likewise a property of the
sweep grid, not a forecast.

**4. `accident_risk_score` is partly circular within the feature set.** It is
derived from `traffic_level`, `weather_risk` and `road_type_score`, then given to
the model alongside all three. Its 0.2465 importance therefore overstates its
independent contribution and understates its parents'. A cleaner design would
drop it, or keep it and drop the parents.

**5. The ordinal structure is not modelled.** Excellent→Very Poor is an ordered
scale, but the classifier treats the five as unrelated categories. The confusion
matrix shows it learned the ordering anyway from the features, but an ordinal
model would encode it directly and should do better near the boundaries.

**6. Explanations are ablation-based, not Shapley values.** Each explanation is
produced by resetting one feature to its dataset median and measuring the drop in
the predicted class's probability. This is honest, cheap (all 19 variants in one
batched call) and genuinely reflects the fitted model — but it measures each
feature in isolation and so does not account for interactions the way SHAP would.

### What it would take to validate this properly

1. **Real labels.** Historical incident, congestion and road-closure records from
   Vejdirektoratet, joined to route and timestamp. Without a real target, no
   amount of modelling makes the accuracy figure meaningful.
2. **Real traffic.** A live or historical traffic feed to replace the derived
   `traffic_level`, which is currently the second-largest lever in the model.
3. **Real roadworks.** Vejdirektoratet publishes planned works; that would
   replace `construction_risk_score` entirely.
4. **Temporal validation.** Train on one period and test on a later one, rather
   than a random split, so the evaluation reflects forecasting rather than
   interpolation.
5. **Calibration.** Check whether a stated confidence of 0.86 corresponds to
   being right 86 % of the time, with a reliability diagram. Nothing in this
   project currently tests that.
