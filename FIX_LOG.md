# Fix Log

Every defect found in the Denmark Road Assistant, what a user would have seen,
why it happened, and what was done about it.

Each entry is written so it can be read aloud in a viva. Where a claim in the
original audit turned out to be wrong, that is recorded too — getting the
diagnosis right matters as much as getting the fix right.

**Totals:** 3 blockers, 3 functional bugs, 5 machine-learning defects and 7
security/hygiene issues from the original audit, plus **79 further defects**
found by a second, parallel audit of the same code. The most serious of the new
ones are documented here alongside the originals.

---

## Blockers — the app did not run

### B1 · The Android project would not open

**What you saw.** Cloning the repository and opening `frontend/android` in
Android Studio failed before any code was compiled.

**Why.** `settings.gradle` and `app/build.gradle` refer to a module called
`capacitor-cordova-android-plugins`, and `app/capacitor.build.gradle` applies a
script from inside it. That folder is generated by `npx cap sync android` and is
deliberately git-ignored, so it is absent in a fresh clone.

**Correction to the original diagnosis.** The audit said Gradle fails with
*"Project with path ':capacitor-cordova-android-plugins' could not be found"*.
That is not what happens. Because `settings.gradle` does `include` the project,
the path resolves and Gradle only emits a **deprecation warning** about the
missing directory. The first **hard** failure is one line later, in
`app/capacitor.build.gradle`: `Could not read script
.../cordova.variables.gradle as it does not exist`. Same root cause, different
message — worth knowing if you are searching for the error.

**Fix.** This is expected behaviour for a Capacitor project, so the fix is
documentation rather than code: README §8 now opens with the requirement to run
`npm run build:android && npx cap sync android` **before** the Android project
will open, and explains why the folder is not committed.

*Files:* `README.md`

### B2 · The Android app could not reach the backend at all

**What you saw.** On an emulator, every request failed. The app looked completely
dead. On one particular phone, on one particular Wi-Fi network, it worked
perfectly — which is why this survived so long.

**Why.** Three rules combining:

1. `network_security_config.xml` permitted cleartext HTTP for exactly one host,
   `192.168.1.103`, and had **no `<base-config>`**.
2. From `targetSdk` 28 onward Android denies cleartext HTTP by default, and this
   app targets 35.
3. `android:usesCleartextTraffic="true"` in the manifest — which looks like it
   grants permission — is **ignored entirely** whenever a network-security-config
   is present.

So every host except that one LAN address was blocked, including
`http://10.0.2.2:8080`, which is the address `environment.android.ts` tries
*first*. `10.0.2.2` is the emulator's alias for the host machine, so the emulator
could never connect.

**Fix.** The config now has an explicit `<base-config
cleartextTrafficPermitted="false">` — everything is HTTPS-only by default — plus
a `<domain-config>` permitting cleartext for the four hosts development actually
uses: `10.0.2.2`, `localhost`, `127.0.0.1` and the LAN address. The file carries
a long comment explaining the three rules above and how to change the LAN
address. The misleading `usesCleartextTraffic` attribute was removed from the
manifest and replaced with a comment saying why.

*Files:* `frontend/android/app/src/main/res/xml/network_security_config.xml`,
`frontend/android/app/src/main/AndroidManifest.xml`, `README.md`

### B3 · The backend would not start

**What you saw.** `./mvnw spring-boot:run` failed with a HikariCP connection
error against `localhost:3306`, on a machine with no MySQL installed. The README
promised that H2 was the default.

**Why.** `application.properties` defaulted to
`jdbc:mysql://localhost:3306/road_assistant` with username and password both
`root`. The README and the configuration said opposite things, and the
configuration won.

There was a second, separate bug hiding behind it: `driver-class-name` was pinned
to `com.mysql.cj.jdbc.Driver` *independently of the URL*. So even if you set
`SPRING_DATASOURCE_URL` to an H2 address, Spring still loaded the MySQL driver
and startup failed with a confusing error.

**Fix.** The default is now a file-based H2 database created automatically at
`backend/data/`. MySQL moved to `application-mysql.properties`, activated with
`-Dspring-boot.run.profiles=mysql`. `driver-class-name` is gone entirely — Spring
infers it from the URL. A third profile, `dev`, adds the H2 console and SQL
logging.

**Verified.** The backend starts on a machine with no MySQL and
`GET /api/health` returns `{"status":"ok"}`.

*Files:* `backend/src/main/resources/application.properties`,
`application-mysql.properties` (new), `application-dev.properties` (new)

## Functional bugs

### F1 · Every helpful error message was replaced by "Something went wrong"

**What you saw.** Whatever went wrong — the Python service not running, a place
name that could not be found, a bad request — the app said
*"Something went wrong on the server."* and nothing else.

**Why.** Two independent faults in the same class.

`ApiExceptionHandler` declared `@ExceptionHandler(Exception.class)`. A
`ResponseStatusException` **is** an `Exception`, and no handler was more specific,
so Spring routed every one of them to the catch-all. All the carefully written
messages the code raised were discarded on the way out.

Worse, the catch-all **logged nothing**. The exception was swallowed without
being printed. A failing signup produced a useless message on screen *and* a
completely silent server log, so there was no way to find out what had happened.
This second half was not in the original audit and was found while testing.

**Fix.** `ResponseStatusException` now has its own handler, which is more specific
than the catch-all and therefore always wins; it preserves the original status
and reason. Every 5xx is logged with a full stack trace under a short reference
id that is also shown to the user, so a screenshot can be matched to a log line.
Handlers were added for unreadable JSON, database constraint violations and
unknown URLs.

**Verified.** Stopping the ML service and analysing a route now returns
`502 "The road-condition model service is unavailable. Start the Python
ml-service on port 8000."` An unknown place returns
`404 "Could not match \"Zzzqqxwv Nowhereville\" to a place in Denmark."`

*Files:* `backend/src/main/java/com/example/backend/exception/ApiExceptionHandler.java`

### F2 · Changing your email logged you out of your own account

**What you saw.** You edit your email on the profile page. It appears to work —
"Profile updated successfully." Then the *next* thing you do fails with a raw
HTTP 500, and reloading the app silently dumps you at the login screen.

**Why.** Three things stacked.

1. The JWT's subject was the user's **email address**. After the update, the
   token in the browser named an address that no longer existed.
2. `CustomUserDetailsService` threw `ResourceNotFoundException` when it could not
   find that address. But it was called from `JwtAuthenticationFilter`, which is
   a **servlet filter** — it runs before Spring MVC, so `@RestControllerAdvice`
   never sees anything it throws. The container turned it into a bare 500.
3. `PUT /api/users/me` returned only the updated user, never a new token, so the
   client had no way to recover.

**Fix.** All three, because any one alone leaves a gap.

* The JWT subject is now the **user's database id**, which never changes. The
  email is still carried as an ordinary claim for readability, but nothing
  authenticates on it. `CustomUserDetailsService` gained `loadUserById`.
* `JwtAuthenticationFilter` now **never throws**. Every failure is recorded as a
  friendly message on the request and the chain continues unauthenticated, so
  Spring Security's entry point produces a clean 401 carrying that message.
* `PUT /api/users/me` returns `{token, user}` — the same shape as login — and the
  frontend stores the new token.

**Verified end to end.** Change the email, then call a protected endpoint with
the **original** token: HTTP 200. It used to be a 500.

*Files:* `security/JwtService.java`, `security/JwtAuthenticationFilter.java`,
`security/CustomUserDetailsService.java`, `service/UserService.java`,
`controller/UserController.java`, `frontend/src/app/auth.service.ts`

### F3 · The feature vector described two different days at once

**What you saw.** Nothing visible — which is what makes it dangerous. The
prediction was quietly computed for the wrong day.

**Why.** In `FeatureEngineeringService.deriveFeatures`, `timeOfDay` came from the
departure time the user chose, but `dayOfWeek` and `season` came from
`ZonedDateTime.now()`. A trip planned for 08:00 on Saturday, entered on a
Tuesday, was scored as *Saturday's hour with Tuesday's weekday pattern*.

**Fix.** There is now one resolved departure instant, and the hour, the weekday
and the season all come from it. The chosen time is interpreted as its next
occurrence — today if it has not passed, otherwise tomorrow — which is what
someone setting "07:00" at nine in the evening means, and it also keeps the
request inside Open-Meteo's forecast window.

*Files:* `routing/RouteObservationService.java` (replaces
`FeatureEngineeringService.java`)

## Machine learning

### M1 · "Very Poor" could never be predicted

**What you saw.** An app advertising a five-grade advisory that in practice had
four. The worst grade was unreachable no matter how bad conditions were.

**Why.** "Very Poor" was **122 of 12 000** training rows — 1.02 %. The shipped
model's own report scored it **precision 0.00, recall 0.00, f1 0.00**, and its
confusion-matrix row was `[5, 3, 3, 13, 0]`: 24 genuinely severe routes, every
one graded as something milder, and an entirely empty prediction column.

The root cause was upstream of the model. The generator derived all weather from
a three-value lookup on the season, so genuinely severe weather **did not exist
in the training data**. The class could not be learned because it was barely
present.

**Fix.** Not by relabelling. The generator now samples weather from stratified
severity bands — calm, mild, wet, severe, extreme — including storms with
hurricane-force gusts, which Denmark genuinely gets. Severe conditions now occur
often enough to be learnable. `class_weight="balanced_subsample"` supports the
rarer grades.

**Result:** Very Poor is 8.03 % of rows, and scores **precision 0.865, recall
0.896, f1 0.880**.

**Verified.** A 1 536-combination sweep of real route/season/day/weather/hour
grids produces all five grades. The breakdown shows the model reacting to the
input rather than to a prior: calm weather yields Excellent 183 / Good 182 /
Moderate 19 and never Poor; storms yield Poor 251 and Very Poor 55 and never
Excellent.

*Files:* `ml-service/app/dataset.py`, `ml-service/app/features.py`,
`ml-service/app/main.py`, `ml-service/scripts/live_distribution_sweep.py`

### M2 · Train/serve skew — the model was extrapolating on nearly every request

**What you saw.** Predictions clustering into a couple of grades regardless of
what you asked for.

**Why.** Features were derived **twice, in two languages**: once by the Java
backend at prediction time, once by the Python service when generating training
data. The two had drifted apart. Measured live vectors occupied roughly **8 % of
the training distribution**.

**Corrections to the original diagnosis.** The audit named four features as
differing. Only three actually did — `construction_risk_score`,
`accident_risk_score` and `vehicle_load_factor`. **`weather_risk` was
character-for-character identical** in both languages, so it was not a formula
mismatch at all.

More importantly, the audit missed the dominant cause. The Java code had a
`lowTrafficTime` branch, and a `timeScore` of `0.05` for night hours, with **no
counterpart in the training generator at all** — Python returned `0.25` for the
same hours. Since `traffic_level` was the single most important feature, this one
mismatch roughly halved it for every departure between 22:00 and 07:00, making
night trips look far better than anything the model had been taught.

**Fix — the structural one.** There is now exactly **one** feature derivation,
`ml-service/app/features.py`. The dataset generator calls it to build training
rows; the prediction endpoint calls it on live input. The Java code that computed
features is deleted. The backend sends only raw observations — distance,
duration, one departure instant, an urban signal and the real weather — and
receives the derived vector back.

Skew is not corrected; it is **structurally impossible**, because there is no
second copy of the formulas left to drift.

**Verified.** Across 1 536 live combinations, every feature's live range now sits
inside the training range with **≥ 99 % coverage** (lowest: 99.3 %).

*Files:* `ml-service/app/features.py` (new), `ml-service/app/dataset.py` (new),
`backend/.../routing/RouteObservationService.java` (new),
`FeatureEngineeringService.java` (deleted), `dto/RouteObservationDto.java` (new)

### M3 · The "noise" function was not random

**What you saw.** The same city pair returning suspiciously stable predictions.

**Why.** `FeatureEngineeringService.noise()` computed its multiplier from
`origin.displayName().length() + destination.displayName().length()` — the
**number of characters in the two place names**, mod 7. It was a pure function of
two string lengths and contained no random number generator at all.

**Corrections to the original diagnosis.** The audit's claim that "the same city
pair always produces byte-identical features forever" is **false** — the day, the
season and the live OSRM distance still vary. But the defect is *worse* than
described in two ways the audit missed:

* the **same** multiplier was applied to all eleven noised features, so the
  perturbations were perfectly correlated, where training drew an independent
  value per feature — the jitter could not decorrelate anything;
* it **compounded**, because `urbanScore` noised internally, `trafficLevel`
  noised the result again, and `accidentRisk` a third time, reaching about **9 %**
  rather than the intended 3 %.

It was also silently dependent on OpenStreetMap: editing a place's label changed
the "seed".

**Fix.** Removed entirely. Training data now uses a properly seeded
`numpy.random.Generator`, and **serving uses no jitter at all** — a given route at
a given time always produces the same answer, which is the correct behaviour for
a prediction anyway.

*Files:* `ml-service/app/features.py`, `FeatureEngineeringService.java` (deleted)

### M4 · The app showed real weather next to a prediction that ignored it

**What you saw.** A genuine Open-Meteo forecast on screen — "12 °C, light rain" —
beside a road-condition grade computed as though it were an average autumn day.

**Why.** The frontend called Open-Meteo purely for display. The model's five
weather features — `weather_risk`, `rainfall_mm`, `humidity`, `wind_speed_kmh`
and `temperature_c` — were all derived from a lookup on the **season alone**.

**Fix.** A new `WeatherService` in the backend fetches the hourly Open-Meteo
forecast for the **midpoint** of the route (a better single sample than either
endpoint for a trip that may cross the country) at the departure hour, and passes
the real values through to the model.

`weather_risk` is now derived from those real numbers by a documented,
explainable formula rather than a season lookup:

> rain 45 % (10 mm/h is heavy rain in Denmark, treated as the ceiling) ·
> ice 30 % (full weight at or below freezing, half between 0 and 3 °C) ·
> wind 25 % (starts to matter around 15 km/h, severe by 60) ·
> humidity 10 % as a proxy for mist and fog, counting only above 70 %

If Open-Meteo cannot be reached the request still succeeds: a seasonal estimate is
substituted and **flagged** as `source: "seasonal-estimate"`, which the UI shows,
so the user is never misled about which they are looking at.

**Verified.** A live analysis used temperature 14.6 °C, rainfall 0.0 mm, humidity
0.79 and wind 27.7 km/h — identical to what Open-Meteo returns for that midpoint
and hour when queried directly.

*Files:* `backend/.../weather/WeatherService.java` (new),
`dto/WeatherReadingDto.java` (new), `ml-service/app/features.py`

### M5 · The reported accuracy was circular — and, it turned out, not reproducible

**Why.** The labels are produced by a rule, and the model is trained to reproduce
that rule, so accuracy measures how well a Random Forest recovers a hand-written
weighted sum. It says nothing about Danish roads.

**A worse problem, found during this work and not in the original audit.** The
shipped `synthetic_denmark_routes.csv` **could not have been produced by the
generator committed beside it.** Measured directly against the committed code's
own arithmetic:

| Rows the committed generator cannot emit | Count |
|---|---:|
| `wind_speed_kmh < 5.0`, though the code forces `max(5.0, …)` | 149 |
| `avg_speed_kmh < 24.0`, though the lowest sampled band starts at 24 | 2 112 |
| `weather_risk` outside `[0.339, 0.670]` | **5 837** |
| `rainfall_mm > 6.18`, above the arithmetic maximum | 1 451 |

`weather_risk` held 89 distinct values spanning 0.00–0.90, where the code can emit
three values ±3 %. **The model answering requests had been trained by code that
was never committed**, so its 0.7788 accuracy belonged to a dataset nobody could
regenerate.

**Fix.** The dataset and model now regenerate deterministically from seed 42, and
a test asserts that two calls to `generate_dataset(200, seed=7)` produce identical
frames. `MODEL_EVALUATION.md` has a full LIMITATIONS section stating plainly that
the labels come from a rule, that accuracy against that rule is partly circular,
that only the weather inputs are real, and what would be needed to validate
against genuine Danish road data.

*Files:* `MODEL_EVALUATION.md`, `ml-service/app/dataset.py`, `ml-service/tests/`

## Security and hygiene

### S1 · The token signing key was published in the repository

`application.properties` carried the fallback
`change-this-demo-secret-key-change-this-demo-secret-key`. Anyone who read the
repository could forge a login token for any account on any deployment that had
not overridden it. The datasource password defaulted to `root`.

**Fix.** New `JwtKeyConfig`. It reads `APP_JWT_SECRET`; **refuses to start**
under a `prod`/`production`/`staging` profile if it is missing; rejects the old
leaked value by name; rejects any secret under 32 characters (which previously
failed as an opaque 500 on every login); and otherwise generates a random
development key with a loud, plain-English warning. No usable default remains in
any committed file.

*Files:* `config/JwtKeyConfig.java` (new), `application.properties`, `.env.example`

---

### S2 · Anyone could trigger a full model retrain

`POST /api/retrain-model` was `permitAll`. Each anonymous call regenerated a
12 000-row dataset, fitted a 280-tree forest and overwrote the dataset, the model
and the metadata **on disk**. Called in a loop it exhausts CPU and disk, and it
changes every other user's predictions underneath them.

**Fix.** It now requires authentication. Route analysis stays public, because the
project must be demonstrable without an account.

**Verified.** Anonymous `POST /api/retrain-model` returns 401.

*Files:* `config/SecurityConfig.java`

---

### S3 · The public model endpoint leaked filesystem paths

`GET /api/model-info` returned `E:\sw8-maps\ml-service\data\...` and
`E:\sw8-maps\ml-service\models\...` to any anonymous caller — the directory
layout of a machine that is not even the one running the code.

**Fix.** `datasetPath` and `modelPath` removed from `ModelInfoDto`, from the ML
service's response model, and from the frontend interface. The endpoint now
returns only the model name, sample count, accuracy, labels and feature
importances.

**Verified.** The response contains no filesystem paths.

*Files:* `dto/ModelInfoDto.java`, `ml-service/app/main.py`,
`frontend/src/app/route-analysis.page.ts`

### S4 · The ignore file had the wrong name, so Git never read it

The root ignore file was called **`.gitignore.txt`**. Git only reads
`.gitignore`, so every rule in it was inert. The consequences were already in the
project: committed `__pycache__/*.pyc`, a stray lock artefact
`main.cpython-313.pyc.2444357645200`, an **82 MB** `road_condition_model.joblib`,
and a nested `backend.zip`.

**Fix.** Renamed to `.gitignore` and extended to cover `node_modules/`, `dist/`,
`target/`, `__pycache__/`, `.venv/`, `.env`, `*.joblib`, `*.zip`, H2 database
files, `logs/`, and the generated
`frontend/android/capacitor-cordova-android-plugins/`. The junk was deleted.
`backend.zip` was confirmed to be a stale Spring Initializr skeleton whose only
unique file was a boilerplate `HELP.md`, and removed. A `.gitattributes` was
added so line endings are stable across platforms.

**Verified.** `git ls-files` contains no `.pyc`, no `.zip`, no `.joblib` and no
`node_modules` — 185 files tracked.

*Files:* `.gitignore`, `.gitattributes`

### S5 · The app disagreed with itself about its own identity

`capacitor.config.ts` declared `appId: 'com.ahmed.roadassistant'` while the
Android project used `com.denmarkroadassistant.app` for both `applicationId` and
`namespace`. Capacitor writes its value into generated files during `cap sync`.

**Fix.** `capacitor.config.ts` now says `com.denmarkroadassistant.app`.

*Files:* `frontend/capacitor.config.ts`

### S6 · The README described a different project on a different computer

It hard-coded `E:\sw8-maps` paths, gave PowerShell-only commands, claimed H2 was
the default when the configuration said MySQL, had **no prerequisites section at
all**, documented 4 of the 14 endpoints, and omitted the entire history and
feedback feature.

**Fix.** Rewritten completely. No absolute paths, commands for both shells, a
prerequisites table with versions, first-time setup, how to run and test, how to
switch database, the Android steps, the full endpoint table, and a
troubleshooting section listing the **real error messages** a user will hit and
what each one means.

*Files:* `README.md`

### S7 · A loaded gun in the security configuration

`SecurityConfig` carried a permanent `permitAll` rule for `/h2-console/**` and a
globally relaxed `frameOptions`, while the H2 console itself was never enabled.
Dead configuration — but the moment anyone set `spring.h2.console.enabled=true`
(which the old README actively invited by claiming H2 was the default) it would
have become an **unauthenticated SQL shell over the entire database**, with no
change to any security code.

**Fix.** The permission and the console now travel together in
`DevH2ConsoleConfig`, which is active only under the `dev` profile *and* only
when the console property is genuinely on. `frameOptions` is scoped to that one
filter chain instead of the whole application.

*Files:* `config/SecurityConfig.java`, `config/DevH2ConsoleConfig.java` (new)

## Further defects found by the second audit

The most serious of the 79 additional findings.

### The security chain was default-open

`authorizeHttpRequests` ended with `anyRequest().permitAll()`. Every endpoint
added in future would have been public unless somebody remembered to list it.
Now `anyRequest().authenticated()` — private by default, public by choice.

*File:* `config/SecurityConfig.java`

### The login token was sent to third parties

The Angular auth interceptor attached the `Authorization` header to **every**
outgoing request, including calls to Open-Meteo and Nominatim. The user's session
token was being handed to unrelated services. It is now attached only to requests
aimed at this app's own backend.

*File:* `frontend/src/app/auth.interceptor.ts`

### A dead session still looked logged in

Nothing in the frontend handled a 401. The route guard only checked that a token
string existed, so after 24 hours a user carried on using an app that had
silently stopped saving anything. A 401 now clears the session and returns the
user to the login page with an explanation.

*Files:* `frontend/src/app/auth.interceptor.ts`, `auth.service.ts`

### The one honesty label in the UI was pointing at the wrong thing

The only synthetic-data disclosure anywhere in the interface was a single hero
kicker — and it described the **weather** as synthetic. That is precisely
backwards: the weather is the one genuinely real input. The wording across the
frontend, the backend's disclaimer constant and the ML service's disclaimer
string now tell the same true story: **real weather, modelled road grade**.

*Files:* `frontend/src/app/*`, `controller/RouteAnalysisController.java`,
`ml-service/app/main.py`

### No timeouts on the public map services

`GeocodingService` and `OsrmRoutingService` were built from the auto-configured
`RestClient.Builder` with no connect or read timeout — the default is to wait
forever. Nominatim and OSRM are free shared endpoints with no service guarantee.
If one stalled rather than refusing the connection, each analysis request parked
a Tomcat worker thread indefinitely; enough of those and the backend stops
answering anything, including its own health check. Now 5 s connect, 15 s read.

*File:* `config/HttpClientConfig.java` (new)

### The ML client threw away its own error detail

`MlServiceClient.ensureSuccess` built a precise message naming the status and
body the ML service returned — and then the surrounding `catch (Exception)` in
the same method caught it and replaced it with the generic fallback text. It now
rethrows its own `ResponseStatusException` unchanged.

*File:* `ml/MlServiceClient.java`

### "Place not found" was reported as a gateway failure

A simple typo returned `502 Bad Gateway`, which reads as "the server is broken".
It is now `404`, and quotes back what the user actually typed.

*File:* `routing/GeocodingService.java`

### The urban score could not tell the two endpoints apart

`urbanScore` searched the **two place names glued into one string** for city
names. So an origin of Copenhagen made the *destination* look like a city too,
and vice versa — the score could not distinguish them. Because it searched the
whole Nominatim label it also matched administrative areas ("Roskilde Kommune,
Region Sjælland") rather than the place itself. Each endpoint is now scored
separately from the first component of its own label, falling back to Nominatim's
`importance` value for anywhere not in the table, and the two are averaged.

*File:* `routing/GeocodingService.java`

### Lombok put the password hash in `toString()`

`AppUser` carried Lombok's all-in-one data annotation, which generated a
`toString()` covering **every** field including `passwordHash`, so any log line or
debugger that printed a user exposed the stored BCrypt hash. It also generated
`equals`/`hashCode` across all fields, which is unsafe for a JPA entity whose
fields change while attached to a persistence context. Nothing called the single
getter it provided, so Lombok was removed from the project entirely.

*Files:* `entity/AppUser.java`, `backend/pom.xml`

### The explanations had nothing to do with the model

The "influential features" list was a chain of `if` statements with fixed
thresholds — hand-written text that never consulted the fitted model. For a
project whose title is *Explainable Machine-Learning*, the explanations were not
explanations at all.

Each feature is now reset to its dataset-typical value, the model is asked again,
and the drop in the predicted class's probability is measured. All nineteen
variants go through in one batched call, so it costs about one extra prediction.
The list is genuinely ordered by measured influence. Its limitations (ablation,
not Shapley values) are stated in `MODEL_EVALUATION.md`.

*File:* `ml-service/app/main.py`

### Deprecated and dead Spring Security configuration

The explicit `DaoAuthenticationProvider` bean used a constructor deprecated in
Spring Security 6.4, produced a warning on every startup, and was **never
called** — passwords are checked directly in `AuthService.login` and later
requests are authenticated by the JWT filter. Removed. The build now compiles
with no deprecation warnings.

*File:* `config/SecurityConfig.java`

### An 82 MB build output was committed

`road_condition_model.joblib` was 82 MB and tracked in Git. Reducing the forest
from 280 unlimited-depth trees to 200 trees of depth 18 with
`min_samples_leaf=4`, and saving with compression, brought it to **8.9 MB** while
accuracy **rose** from 0.7788 to 0.8546. It is now git-ignored as a build output
and regenerates from nothing in about five seconds.

*Files:* `ml-service/app/main.py`, `.gitignore`

### Miscellaneous

* `@app.on_event("startup")` replaced with FastAPI's `lifespan`.
* The ML service printed **every request payload** to stdout, putting user route
  data in the server log on every request. Removed.
* `.env.example` listed four of the nine environment variables the backend reads,
  omitting all five database ones — precisely the settings you needed to obtain
  the configuration the README promised. Now complete.
* `android:allowBackup="true"` with no backup rules meant the login token in the
  WebView's local storage was copied into the user's cloud backup. Now off.
* `androidScheme: 'http'` served the app from a non-HTTPS origin, relying on the

## Found by the user after the repair loop

### You could only choose a time, never a date

**What you saw.** The form offered a departure *time* and nothing else. There was
no way to ask about next Saturday, or about a trip in January.

**Why.** The request carried only a string like `"17:00"`, and the server guessed
the date for you: today, or tomorrow if that time had already gone.

```java
LocalDate date = now.toLocalDate();
if (chosen.isBefore(now.toLocalTime())) {
    date = date.plusDays(1);
}
```

**Why it mattered more than it looked.** `day_of_week` and `season` are two of the
model's nineteen features. With no date they could only ever hold today's or
tomorrow's value, so neither could be varied — and `season` in particular is what
makes the model swing between grades. The app could not demonstrate its own most
interesting behaviour.

**Fix.** A date picker was added, and the resolved instant is now built from the
date and the time together. The picker is limited to **today plus the next six
days**, matching how far Open-Meteo forecasts, and a date outside that range is
refused with a 400 that names the allowed window. That limit is deliberate: the
app's central claim is that the weather behind every grade is a real forecast, so
it declines to answer rather than silently substituting a seasonal average.
`RouteObservationService.FORECAST_WINDOW_DAYS` is the single source of that number
and `WeatherService` reads it, so the two cannot drift apart.

History now stores the resolved departure (`2026-09-15 17:00`) instead of a bare
time, so an old entry still says which day it was predicted for. The column was
widened from 10 to 16 characters to fit.

**Verified.** The same route at 08:00 on two different days returns
`dayOfWeek: wednesday` with a 14.9 °C forecast and `dayOfWeek: saturday` with a
13.9 °C forecast — different day, different real weather. A date nine days out
returns 400 *"The weather forecast only reaches 2026-09-15…"*, and yesterday
returns 400 *"That date has already passed."* Five tests cover the window
boundaries and the rejections.

### Roadworks and incidents on your route (new feature)

**Asked for by the user:** "can I find is it under construction or technical issue".

**What the app did before.** Nothing real. It has a `construction_risk_score`
feature, but it is only:

```python
seasonal_roadworks = {"spring": 0.18, "summer": 0.22, "autumn": 0.12, "winter": 0.05}[season]
construction_risk_score = 0.06 + urban_density * 0.30 + seasonal_roadworks
```

That says *roadworks are likelier in summer and in built-up areas*. It has never
heard of the E45.

**Finding the data.** Vejdirektoratet's published SDK points at
`data.vd-nap.dk`, which **no longer resolves** — `nslookup` returns
"Non-existent domain". Their registered API needs an account and a key. So the
live traffic map at trafikkort.vejdirektoratet.dk was opened, its JavaScript
bundle downloaded, and the host it actually reads extracted from it: a public
Google Cloud Storage object, **no key and no registration**:

```
https://storage.googleapis.com/trafikkort-data/geojson/big-screen-events.json
```

**Two properties of that feed had to be handled, both found by measuring it:**

1. **It keeps recently cleared events.** On one read, **199 of 207** records had
   already ended. Events that finish before the chosen departure time are dropped.
2. **It publishes progressive updates as separate records.** One real queue on the
   E45 appeared **ten times** with ten different end times. Records are collapsed
   by headline, keeping the longest-lasting (the newest revision).

Junction markers arrive as `&lt;56a&gt;`; unescaping them naively leaves `<56a>`
on screen, which reads as broken markup, so they are rendered as "exit 56a".

**Matching.** Each event's WGS84 coordinates are compared against the OSRM route
polyline — a bounding box first, then nearest-vertex distance. OSRM returns a
dense line (~800 points over 36 km), so nearest-vertex is accurate enough at the
150 m threshold and far simpler than point-to-segment projection.

**Deliberately NOT fed to the model.** This is the only genuinely measured road
information in the application, and it is tempting to plug it into
`construction_risk_score`. That would recreate exactly the train/serve mismatch
this project spent its largest phase removing: the model was trained on a
distribution where that feature is an assumption about likelihood, not a count of
real events. The events are shown beside the grade, and the panel says so.

A failure fetching the feed is treated as "no information", never as an error —
the analysis still completes.

**Verified.** Vejle to Aarhus returns three distinct active events, at 31 m, 44 m
and 52 m from the route, including *"Advarsel - E45 fra Vejle mod Aarhus mellem
exit 56a Horsens V og exit 55 Horsens N"*. Copenhagen to Roskilde returns none,
correctly. 11 unit tests cover the distance maths, the bounding box and the text
tidying, without touching the network.

### The UI hid most of what the app had already computed

**What you saw.** A screenshot of another build of this project showed grade
probability bars, a grid of derived features, feature-importance bars, sample
route buttons and a retrain control. This build showed none of them.

explaining itself into a void.

(For the record: the screenshots were from a different copy of the app, not this
repository at an earlier commit. They show accuracy 78%, the pre-repair
disclaimer wording, and a season-guessed 8.22 °C spring temperature - all of
which this build had already moved past.)

**Fix.** Four sections added, all bound to data that already existed:

* **Grade Probabilities** - all five grades with animated bars, the predicted one

* **Derived Route Features** - all nineteen inputs as a grid. This is the

* **Top Feature Importance** - what matters across the whole forest, captioned to

### Turn-by-turn guidance ("Start my journey")

**Asked for by the user:** navigation like Google Maps, following GPS.

**What was missing.** The route request asked OSRM for
`overview=full&geometries=geojson` only. That returns the *shape* of the route -
enough to draw a line, not enough to guide anyone along it. There were no
instructions at all.

**Backend.** The request now adds `steps=true`, and each manoeuvre is turned into
a sentence. OSRM ships no human wording on purpose - it returns a type and a
modifier and leaves phrasing to the client so it can be localised - so
`turn` + `left` + `Vestergade` becomes *"Turn left onto Vestergade"*, and
`roundabout` + `exit: 3` becomes *"At the roundabout, take exit 3"*. Each step is
also matched to the nearest point on the overall route line; that index is what
lets the app know how far along the driver already is without re-measuring the
whole route on every GPS fix.

**Frontend.** A new `NavigationService` holds the maths and deliberately touches
no map, no DOM and no browser API, so it can be reasoned about on its own:
great-circle distance, nearest point on the route, which step is being driven,
distance to the next manoeuvre, distance and time remaining, and off-route
detection.

Progress is tracked by **position along the route line**, not by distance to the
next turn. That matters on a route that doubles back on itself, where a driver
can be physically close to a manoeuvre they passed twenty minutes ago.

The page adds a **Start my journey** button, a live guidance panel (big distance,
current instruction, the one after it, remaining distance, time left and arrival
clock), a full **Directions** list with the current step highlighted, a GPS dot
that the map pans to follow, and spoken guidance through the browser's own speech
synthesiser at 1 km, 400 m and at the turn - each said once, tracked so a GPS tick
cannot repeat it. Voice has a mute toggle. Leaving the route by more than 60 m
triggers one spoken warning, not one per fix. The watch is cleared on
`ngOnDestroy`, so it cannot keep running after the page is gone.

**Honest limitations, stated on screen:** it follows this device's GPS, it does
**not** re-route around traffic, and the road-condition grade is not recomputed
while driving. A desktop browser will not move, so it is only meaningful on a
phone or in the Android build.

**Verified** by feeding simulated GPS fixes along the real Copenhagen-Roskilde
geometry: the panel tracked to *"3.3 km - Turn left onto Vigerslevvej, then Turn
right onto Folehaven"*, remaining 32 km / 25 min / arrive 09:05, step 12
highlighted in the list, GPS marker drawn, and the journey ended itself on
arrival. Seven tests cover the instruction wording, including unnamed roads,
roundabout exits and unknown manoeuvre types.

### start-all.ps1 could not start anything at all

**What you saw.** Running `.\start-all.ps1` printed the banner, said it was
starting the ML service, and then immediately shut down again with:

```
Start-Process : Cannot validate argument on parameter 'ArgumentList'.
The argument is null, empty, or an element of the argument collection contains a null value.
At start-all.ps1:77
```

**Why.** The helper function took its command-line arguments in a parameter
called `$Args`. That is a **reserved automatic variable** in PowerShell - it
already holds whatever was passed to the enclosing function - so a parameter of
that name never receives the caller's value. `Start-Process` was handed nothing
and refused. The Bash script was unaffected, which is why this survived: the
`.sh` version had been run end to end, but the `.ps1` had only been read, not
executed. That was a gap in how it was verified, not just a typo.

**Fix.** The parameter is renamed `$ProcessArgs`, at the declaration and all three
call sites, with a comment recording why that name is forbidden.

**Verified** by actually running `powershell -File start-all.ps1` and watching all
three services come up.

*Files:* `start-all.ps1`
